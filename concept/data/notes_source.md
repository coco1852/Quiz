| 단원 | 문제 유형 | 풀이 시작점 | 단골 함정 | 위치 |

# PART 1. 데이터베이스

## 1. 3단계 스키마 & 데이터 독립성

**한 칼 구분: 논리는 위쪽 경계(외부–개념), 물리는 아래쪽 경계(개념–내부)**
- **논리적 독립성** = **개념** 스키마가 바뀌어도 → 외부 스키마(응용) 영향 X
- **물리적 독립성** = **내부** 스키마가 바뀌어도 → 개념 스키마 영향 X

```
   [외부 스키마1] [외부 스키마2] [외부 스키마3]   ← VIEW · DTO  (여러 개)
          \            |            /
   ─ ─ ─ ─ ─ 논리적 독립성 (외부–개념) ─ ─ ─ ─ ─
                 [ 개념 스키마 ]                  ← 테이블 · @Entity  (DB당 1개)
                       |
   ─ ─ ─ ─ ─ 물리적 독립성 (개념–내부) ─ ─ ─ ─ ─
                 [ 내부 스키마 ]                  ← 인덱스 · 저장구조  (접근 불가)
                       |
                 (( 디스크 ))
```

| 스키마 | 관점 | 키워드 |
|---|---|---|
| 외부 (External) | 사용자·응용 프로그램 | 뷰(View), 서브스키마, 여러 개 존재 가능 |
| 개념 (Conceptual) | 조직 전체 | 전체 논리 구조, 접근권한·제약조건, **DB당 1개** |
| 내부 (Internal) | 물리적 저장 | 저장 구조, 인덱스, 레코드 배치 |

> ⚠️ 선지함정
> - "개념 스키마는 여러 개 존재할 수 있다" → X (외부만 여러 개)
> - 인덱스 추가/저장장치 변경 = **물리적** 독립성 문제
> - 테이블에 컬럼 추가해도 기존 응용 안 고침 = **논리적** 독립성

**Spring 앵커 (네가 확정한 멘탈모델)**

| 단계 | 내 실무 | 개수 |
|---|---|---|
| 외부 | `VIEW`, **DTO** (용도별로 입맛대로 가공) | 여러 개 |
| 개념 | **실제 테이블 · `@Entity`** (원본) | 하나 |
| 내부 | 인덱스 · 디스크 (내가 접근 못 하는 영역) | 하나 |

- 헷갈리면 질문 하나: **"이거 여러 개 만들 수 있나?"** → 여러 개면 외부(VIEW·DTO), 하나뿐인 원본이면 개념
- ~~개념 = DTO~~ → DTO는 API마다 여러 개(`EmpListDto`, `EmpDetailDto`…) 만드니까 **외부**
- `@Entity`는 엄밀히는 DB 테이블 정의를 자바로 비춘 ORM 매핑 → **기억용 앵커**로만 쓰고, 답은 교재 표현("조직 전체의 논리 구조, DB당 1개")으로
- 실무 체감: `CREATE INDEX` 해도 쿼리 한 글자 안 바뀜 = **물리적 독립성** / `ALTER TABLE ADD COLUMN` 해도 기존 뷰·API 안 터짐 = **논리적 독립성** (`SELECT *`는 이걸 깨먹는 안티패턴)
- VIEW로 조회 중이면 그 순간엔 외부 스키마를 보는 것, 테이블 정의 자체를 보면 개념

오답노트 한 줄: `외부=VIEW·DTO(여러개) / 개념=Entity(하나) / 내부=접근불가, 논리=외부-개념 / 물리=개념-내부`

## 2. 릴레이션 용어 (테이블 예시로 즉답)

**[학생] 릴레이션 = 테이블 전체**

```
              ┌──── 차수(Degree) = 3  (애트리뷰트 = 열 개수, 세로) ────┐
              │                                                        │
            ┌──────────┬──────────┬──────────┐
            │  학번    │  이름    │  학과    │  ← 애트리뷰트 (열 이름)
   ┌        ├──────────┼──────────┼──────────┤
   │        │  1001    │  김철수  │  컴공    │
 기수 = 3   │  1002    │  이영희  │  전자    │  ← 튜플 (행 1줄)
(Cardinality)│  1003    │  박민수  │  컴공    │
 튜플 개수  └──────────┴──────────┴──────────┘
   └                                  ↑
                         도메인 = 학과가 가질 수 있는 값의 집합 {컴공, 전자, 기계, ...}
```

| 용어 | 이 테이블에서 | 값 |
|---|---|---|
| 릴레이션 | 테이블 전체 | 학생 |
| 튜플 (Tuple) | 행 1줄 | (1001, 김철수, 컴공) |
| 애트리뷰트 | 열 이름 | 학번, 이름, 학과 |
| 도메인 | 한 애트리뷰트가 가질 수 있는 값의 집합 | 학과 도메인 = {컴공, 전자, ...} |
| **차수 (Degree)** | **애트리뷰트 개수** | **3** |
| **기수 (Cardinality)** | **튜플 개수** | **3** |

**한 칼 구분: 차수=세로(열), 기수=가로(행). "차렷! 세로로 서!" → 차수는 세로.**

> ⚠️ 릴레이션 특성 선지: 튜플 간 **순서 없음**, 튜플 **중복 없음**, 애트리뷰트는 **원자값**. "튜플은 삽입 순서를 유지한다" → X

## 3. 키 (Key)

**한 칼 구분: 슈퍼키 = 유일성만. 후보키 = 유일성 + 최소성. 기본키 = 후보키 중 뽑힌 1개. 대체키 = 안 뽑힌 나머지.**

```
슈퍼키 ⊃ 후보키 = { 기본키(1개) + 대체키(나머지) }
```

| 키 | 유일성 | 최소성 | 비고 |
|---|---|---|---|
| 슈퍼키 | O | X여도 됨 | (학번+이름)도 슈퍼키 |
| 후보키 | O | O | 기본키 자격 있는 것들 |
| 기본키 | O | O | **NULL 불가, 중복 불가** |
| 대체키 | O | O | 후보키 − 기본키 |
| 외래키 | — | — | 다른 릴레이션의 기본키 참조. **NULL 가능**, 중복 가능 |

**예시 문제**: 학생(학번, 주민번호, 이름, 학과), 학번·주민번호 각각 유일.
- 후보키: {학번}, {주민번호} → 2개
- 기본키를 학번으로 → 대체키 = 주민번호
- (학번, 이름)은? → 슈퍼키 O, 후보키 X (최소성 위반)

> ⚠️ 선지함정
> - "외래키는 NULL을 가질 수 없다" → X (기본키가 NULL 불가)
> - "후보키는 릴레이션에 하나만 존재한다" → X (기본키가 1개)
> - 무결성 연결: 개체 무결성=기본키 NULL·중복 X / 참조 무결성=외래키는 참조 릴레이션의 기본키 값 or NULL

> ② 후보키가 되기 위해서는 유일성과 효율성을 둘 다 만족해야 한다.

> ④ 참조 무결성을 위해 참조 대상이 존재하지 않는 외래키를 허용하지 않는다.  
> ⑤ 후보키는 … 최소성을 만족하지 않는다.  
>
> **→ 정답 ④** — ② 효율성 X → **최소성**. ③ 슈퍼키 X → **대체키**. ⑤ 최소성 만족해야 후보키.

> **📝 기출 | 2021 국회직 #14**
>
> 유일성은 만족하지만 최소성은 만족하지 못하는 키는?
>
> ① 기본키  
> ② 대체키  
> ③ 복합키  
> ④ 후보키  
> ⑤ 슈퍼키  
>
> **→ 정답 ⑤** — "유일성만" = 슈퍼키. 기본·대체·후보는 전부 최소성까지 만족.

## 4. 정규화 (1NF → BCNF)

**한 칼 구분: "원자값(1) → 부분 제거(2) → 이행 제거(3) → 결정자가 전부 후보키(BCNF)"**
암기: **원-부-이-결** (도부이결로도 외움: 도메인 원자값 / 부분 / 이행 / 결정자)

| 단계 | 제거 대상 | 판정 질문 |
|---|---|---|
| 1NF | 반복 그룹, 다중값 | 모든 값이 원자값인가? |
| 2NF | **부분 함수 종속** | 복합키의 **일부**에만 종속된 속성 있나? |
| 3NF | **이행 함수 종속** | 키 아닌 속성 → 키 아닌 속성 있나? (A→B→C) |
| BCNF | 후보키 아닌 결정자 | **모든 결정자가 후보키인가?** |

**알파벳 예시 3종 — 표로 한눈에**

| | 릴레이션 · 키 | 함수 종속(FD) | 걸리는 곳 | 결론 |
|---|---|---|---|---|
| **예시 1** | R(A,B,C,D), 키 (A,B) | (A,B)→C, **B→D** | D가 키의 **일부(B)**에만 종속 = 부분 종속 | **1NF**, 2NF 위반 |
| **예시 2** | R(A,B,C), 키 A | A→B, **B→C** | A→B→C **이행** 종속 | **2NF**, 3NF 위반 |
| **예시 3** | R(A,B,C), 후보키 (A,B) | (A,B)→C, **C→A** | 결정자 C가 **후보키 아님** | **3NF**, BCNF 위반 |

**풀이 시작점**: ① 후보키 확정 → ② FD 좌변(결정자) 하나씩 보며 "부분? 이행? 결정자=후보키?" 순서로 아래에서 위로 판정.

> ⚠️ 선지함정: "정규화하면 조인 연산이 줄어든다" → X (테이블 분해 → 조인 **증가**). 정규화 목적 = 이상(삽입·삭제·갱신 Anomaly) 제거, 중복 최소화.

## 5. 원자성 vs 고립성 (ACID)

**한 칼 구분: 원자성은 트랜잭션 "하나의 안", 고립성은 트랜잭션 "여럿 사이".**

| 성질 | 범위 | 키워드 | 담당 기법 |
|---|---|---|---|
| 원자성 (Atomicity) | 트랜잭션 1개 내부 | All or Nothing, 부분 실행 X | **회복 (Undo)** |
| 일관성 (Consistency) | 실행 전후 상태 | 제약조건 유지 | 무결성 제약 |
| 고립성 (Isolation) | 동시 실행 트랜잭션 **간** | 중간 결과 못 봄 | **동시성 제어 (락, 2PL)** |
| 지속성 (Durability) | Commit 이후 | 결과 영구 반영 | 회복 (Redo) |

판정 요령: 지문에 "**계좌이체 중 장애로 출금만 반영**" → 원자성. "**두 트랜잭션이 동시에 접근해 중간값을 읽음**" → 고립성.

- **원자성 ↔ Undo**(부분 실행 지우기), **지속성 ↔ Redo**(commit한 건 살리기) — 6번과 세트

> ⚠️ 경계혼동 주의: 일관성 vs 고립성. 일관성은 "결과 상태가 규칙을 지키는가", 고립성은 "실행 과정에서 서로 간섭 없는가". (2PL은 고립성, 2PC는 분산 커밋 — 딴 놈이니 섞지 말 것)

>

## 6. 회복 기법 — Undo/Redo · 지연갱신 vs 즉시갱신 · 체크포인트

### 6-0. Undo · Redo가 뭔데?

장애 후 DB를 "약속했던 상태"로 맞추는 **반대 방향 두 연산**.

| | Undo (취소) | Redo (재실행) |
|---|---|---|
| 대상 | **commit 안 한** 트랜잭션 | **commit 한** 트랜잭션 |
| 의미 | 없던 일로 만들기 ("뒤로") | 약속한 건 끝까지 반영 ("앞으로") |
| 로그에서 쓰는 값 | **옛 값 (old value)** | **새 값 (new value)** |
| 지키는 성질 | **원자성** | **지속성** |

예: 로그 `<T, X, 10, 20>` (X를 10→20)
- T가 commit 못 하고 죽음 → **Undo** → X = 10
- T가 commit 했는데 디스크엔 아직 10 → **Redo** → X = 20

왜 필요? DBMS는 성능 때문에 변경을 버퍼(메모리)에 뒀다가 나중에 디스크에 씀 → 장애 순간 "commit 안 했는데 이미 써진 것"(Undo 대상)과 "commit 했는데 아직 안 써진 것"(Redo 대상)이 공존. 그래서 **로그 먼저, 데이터 나중 = WAL (Write-Ahead Logging)**.

Spring 앵커: `@Transactional` 메서드가 예외로 롤백 = Undo / 커밋 응답 직후 서버가 죽어도 데이터 살아있음 = 재기동 시 Redo.

**한 칼 구분: Undo = old로 뒤로, Redo = new로 앞으로. 기준은 오직 commit 로그 유무.**

**commit · rollback · abort 위치 (트랜잭션 상태도)**

```
 활동 ──연산 끝──▶ 부분 완료 ──commit──▶ 완료(Committed)  → 이후 장애 시 Redo
  │                  │
  └──오류·장애──▶ 실패(Failed) ──rollback(Undo)──▶ 철회(Aborted)
```

- commit = 확정 / rollback = 취소(Undo 수행) / abort = 실패 후 철회된 상태(또는 그 처리)
- 부분 완료 = 마지막 연산은 끝났지만 아직 commit 전 → 여기서 장애 나도 **Undo**

### 6-1. 지연갱신 vs 즉시갱신

**한 칼 구분: 지연 = DB에 아직 안 썼으니 지울 게 없다 → Undo 불필요. 즉시 = 이미 썼으니 되돌려야 한다 → Undo 필요.**

| 기법 | DB 반영 시점 | Commit **전** 장애 | Commit **후** 장애 |
|---|---|---|---|
| **지연 갱신 (Deferred)** | Commit 후에 반영 | 아무것도 안 함 (로그 버림) | **Redo** |
| **즉시 갱신 (Immediate)** | 연산 즉시 반영 | **Undo** | **Redo** |

**예시 문제**: 즉시 갱신 로그가 아래와 같을 때 장애 발생. 각 트랜잭션 처리?
```
<T1 start> <T1, X, 10, 20> <T1 commit>
<T2 start> <T2, Y, 30, 40>          ← 여기서 장애
```
→ T1: commit 기록 있음 → **Redo** / T2: commit 없음 → **Undo**

**풀이 시작점**: 로그에서 `<commit>` 유무만 먼저 체크 → commit 있으면 Redo 후보, 없으면 (즉시갱신) Undo / (지연갱신) 무시.

> ⚠️ 선지함정: "지연 갱신은 Undo와 Redo 모두 필요하다" → X (지연 갱신 = **Redo만**, NO-UNDO/REDO)
> - "Redo는 old value를 사용한다" → X (Redo=new, Undo=old)

### 6-2. 체크포인트 + 시스템 실패 (단골 그림)

```
           T1 ●━━━━━commit
           T2    ●━━━━━━━━━━━━━━━━━━━━━commit
           T3       ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┫
           T4                  ●━━━━━━━━━━━commit
           T5                       ●━━━━━━━━━━━━━━━━━┫
   ────────────────────────┊─────────────────────────┃──────▶ 시간
                      체크포인트(CP)              시스템 실패
```

| T | 상황 | 처리 |
|---|---|---|
| T1 | CP **전에** commit | **아무것도 안 함** (CP 때 이미 디스크 반영) |
| T2 | CP 전 시작, 장애 전 commit | **Redo** |
| T3 | CP 전 시작, 장애 때 실행 중 | **Undo** |
| T4 | CP 후 시작, 장애 전 commit | **Redo** |
| T5 | CP 후 시작, 장애 때 실행 중 | **Undo** |

**판정 2단계 (즉시 갱신 기준)**
1. 장애 전에 commit 있나? → 있으면 **Redo**, 없으면 **Undo**
2. 그 commit이 CP보다도 앞이면? → **아무것도 안 함**

> ⚠️ 최다 함정: T1을 Redo로 찍기. **CP 이전에 완료된 트랜잭션은 회복 대상 아님.**
> - 지연 갱신 버전이면 T3·T5는 Undo가 아니라 **그냥 무시**(로그 버림)
> - 체크포인트의 목적 = 회복 시 **로그 전체를 다 훑지 않도록** 탐색 범위 축소

## 7. UNION vs UNION ALL

**한 칼 구분: ALL = "다(All) 나와" = 중복 유지.**

| | UNION | UNION ALL |
|---|---|---|
| 중복 | 제거 | 유지 |
| 내부 동작 | 중복 제거(정렬/해시) 비용 발생 | 그냥 이어붙임 → **빠름** |

**예시**: A = {1, 2, 3}, B = {2, 3, 4}
- UNION → 1,2,3,4 (**4행**)
- UNION ALL → 1,2,3,2,3,4 (**6행**)

> ⚠️ 함정: 두 SELECT의 **컬럼 수와 데이터 타입(순서대로)이 호환**되어야 함. 컬럼 "이름"이 같을 필요는 없음. 결과 행 수 계산 문제 나오면 중복 개수부터 셀 것.


### 🔁 기출로 확인

> **📝 기출 | 2020 국가직 #20 (UNION 호환 조건)**
>
> STUDENT(studno, name, grade, height, deptno), PROFESSOR(profno, name, position, salary, deptno)일 때 오류 없이 동작하는 SQL은?
>
> ① SELECT deptno, position, AVG(salary) FROM PROFESSOR GROUP BY deptno;  
> ② (SELECT studno, name FROM STUDENT WHERE deptno=101) UNION (SELECT profno, name FROM PROFESSOR WHERE deptno=101);  
> ③ SELECT grade, COUNT(*), AVG(height) FROM STUDENT WHERE COUNT(*) > 2 GROUP BY grade;  
> ④ SELECT name, grade, height FROM STUDENT WHERE height > (SELECT height, grade FROM STUDENT WHERE name='홍길동');  
>
> **→ 정답 ②** — UNION은 **컬럼 수·타입(순서대로)만 맞으면** 됨 → studno/profno 이름 달라도 OK. ① position이 GROUP BY에 없음 ③ 집계조건은 HAVING ④ 서브쿼리가 2열.

> 💡 UNION vs UNION ALL 자체를 묻는 문제는 첨부 기출엔 없음 → 위 행 수 계산(4행 vs 6행)만 확실히.

# PART 2. 소프트웨어공학

## 1. 결합도 · 응집도 순서

**한 칼 구분: 결합도는 낮을수록, 응집도는 높을수록 좋다. "결낮응높".**

**결합도 (강함=나쁨 → 약함=좋음)**
```
내용 > 공통 > 외부 > 제어 > 스탬프 > 자료
```
암기: **내공외제스자** ("내 공은 외제, 스스로 자랑")

| 결합도 | 키워드 |
|---|---|
| 내용 | 다른 모듈 내부를 직접 참조·수정 |
| 공통 | 전역 변수 공유 |
| 외부 | 외부 선언 데이터(프로토콜, 통신 포맷) 공유 |
| 제어 | **제어 플래그**(flag) 전달, 상대 논리 흐름 통제 |
| 스탬프 | **구조체·배열 전체** 전달 |
| 자료 | 필요한 **값(파라미터)만** 전달 — 최선 |

**응집도 (낮음=나쁨 → 높음=좋음)**
```
우연 < 논리 < 시간 < 절차 < 통신 < 순차 < 기능
```
암기: **우논시절 통순기** ("우스운 논리도 시절 지나면 통하는 순간이 기막히다")

| 응집도 | 키워드 |
|---|---|
| 우연 | 아무 관계 없는 것들 모임 |
| 논리 | 유사 성격끼리, 파라미터로 골라 실행 |
| 시간 | **같은 시점**에 실행 (초기화 모듈) |
| 절차 | 순서대로 수행, 데이터 연결은 약함 |
| 통신 | **같은 입출력 데이터** 사용 |
| 순차 | **앞 출력 = 뒤 입력** |
| 기능 | 단일 기능 수행 — 최선 |

> ⚠️ 경계혼동 최다 출제
> - 스탬프 vs 자료: 구조체 통째면 스탬프, 값만 뽑아 주면 자료
> - 절차 vs 순차: 출력→입력으로 **데이터가 이어지면 순차**, 순서만 있으면 절차
> - 시간 vs 절차: 순서 상관없이 "같은 때"면 시간(init)
> - "가장 바람직한 결합도는?" → 자료 / "가장 바람직한 응집도는?" → 기능


### 🔁 기출로 확인

>

> - 영희: 우연적 응집도 + 내용 결합도
> - 동수: 기능적 응집도 + 자료 결합도
> - 민희: 논리적 응집도 + 스탬프 결합도
>

> ② 철수, 민희  
> ③ 동수, 영희  
> ④ 동수, 민희  
>
> **→ 정답 ③** — 최선 = 기능 + 자료(동수), 최악 = 우연 + 내용(영희). 양 끝만 알면 바로.

> **📝 기출 | 2018 교육행정 #14**

> ㄱ. 한 구성 요소의 출력이 다른 구성 요소의 입력 → 순차적 응집도

> **📝 기출 | 2026 국가직 #9**
>
> 옳지 않은 것은?
>
> ① 한 모듈이 다른 모듈 내부를 직접 참조하는 경우는 내용 결합도이다.  
> ② 응집도는 모듈 내 구성 요소들이 얼마나 밀접하게 관련되어 있는지를 나타낸다.  
> ③ 한 요소의 출력이 다음 요소의 입력으로 사용되는 경우는 순차적 응집도이다.  
> ④ 레코드, 구조체, 객체 같은 복잡한 데이터 구조를 주고받는 경우는 데이터 결합도이다.  
>
> **→ 정답 ④** — 구조체 통째 = **스탬프** 결합도. 값만 = 자료(데이터).

## 2. 디자인 패턴 (GoF) 분류

**한 칼 구분: 만들면 생성, 감싸고 연결하면 구조, 주고받고 행동하면 행위.**

| 분류 | 패턴 | 한 줄 특징 |
|---|---|---|
| **생성 (5)** | Singleton | 인스턴스 **1개** 보장 (Spring Bean 기본 스코프) |
| | Factory Method | 생성을 서브클래스에 위임 |
| | Abstract Factory | **관련 객체군**을 묶어 생성 |
| | Builder | 복잡한 객체를 단계별 조립 (`@Builder`) |
| | Prototype | 원형 **복제(clone)**로 생성 |
| **구조 (7)** | Adapter | **인터페이스 변환** (호환) |
| | Bridge | 구현부와 추상부 **분리**해 독립 확장 |
| | Composite | 트리 구조, 부분-전체 **동일 취급** |
| | Decorator | 기능을 **동적으로 덧씌움** (Java IO 스트림) |
| | Facade | 복잡한 서브시스템에 **단일 창구** |
| | Flyweight | 인스턴스 **공유**로 메모리 절약 |
| | Proxy | **대리자** 통해 접근 제어 (JPA 지연로딩!) |
| **행위 (11)** | Observer | 상태 변화 시 **일괄 통지** (이벤트 리스너) |
| | Strategy | 알고리즘을 **교체 가능**하게 캡슐화 |
| | Template Method | 골격은 상위, 세부는 하위 재정의 |
| | Command | 요청 자체를 **객체화** |
| | State | 상태에 따라 행위 변경 |
| | Iterator | 내부 구조 노출 없이 순회 |
| | Mediator | 객체 간 통신을 **중재자**로 집중 |
| | Chain of Responsibility | 처리자 사슬 따라 전달 (Filter 체인) |
| | Memento | 상태 **저장·복원** (undo) |
| | Visitor | 구조와 연산 분리 |
| | Interpreter | 문법 규칙을 클래스화 |

암기(생성 5개): **싱팩앱빌프**
> ⚠️ 지문함정: "분류가 다른 하나는?" 유형 — **Facade·Proxy·Adapter·Decorator는 구조**, **Observer·Strategy·State는 행위**만 확실히 박아두면 대부분 컷.

## 3. UML 다이어그램 분류

**한 칼 구분: 그림에 시간·순서·상호작용이 있으면 행위(동적), 구조·관계만 있으면 구조(정적).**

| 구조(정적) | 행위(동적) |
|---|---|
| **클래스** | **유스케이스** |
| **객체** | **시퀀스** (상호작용) |
| 컴포넌트 | 커뮤니케이션(협동) (상호작용) |
| 배치 | 상태(State) |
| 패키지 | 활동(Activity) |
| 복합체 구조 | 타이밍 (상호작용) |

- 클래스: 클래스·속성·연산·**관계**(일반화/집합/합성/의존)
- 객체: 특정 **시점의 인스턴스** 스냅샷 → 그래도 **구조** 다이어그램!
- 유스케이스: 액터-시스템 기능, `<<include>>`(필수 포함) / `<<extend>>`(조건부 확장)
- 시퀀스: **시간 순서**, 생명선(lifeline), 메시지

> ⚠️ 경계혼동
> - "객체 다이어그램은 동적 다이어그램이다" → X (인스턴스지만 **정적**)
> - include vs extend 방향: include는 기본→포함 기능, extend는 확장 기능→기본
> - 시퀀스 vs 커뮤니케이션: 같은 상호작용, 시퀀스는 **시간축**, 커뮤니케이션은 **연결 관계** 강조

## 4. 화이트박스 vs 블랙박스 테스트

**한 칼 구분: 코드(내부 로직)를 보면 화이트, 명세(입출력)만 보면 블랙.**

| | 화이트박스 | 블랙박스 |
|---|---|---|
| 기준 | 소스 코드, 논리 경로 | 요구사항 명세, 입출력 |
| 별칭 | 구조 테스트 | 기능 테스트 |
| 기법 | **기초 경로**, **조건 검사**, **루프 검사**, **데이터 흐름 검사**, 문장/분기 커버리지 | **동치 분할**, **경계값 분석**, **원인-효과 그래프**, 오류 예측, 비교 검사 |

기법 판정 예시:
- "1~100 입력 범위에서 0, 1, 100, 101을 테스트" → **경계값 분석** (블랙)
- "입력을 유효/무효 클래스로 나눠 대표값 선정" → **동치 분할** (블랙)
- "McCabe 순환 복잡도, 독립 경로 수" → **기초 경로 검사** (화이트)
- 순환 복잡도 V(G) = **E − N + 2** (간선 − 노드 + 2) = 분기 수 + 1

> ⚠️ 지문함정: "경계값 분석은 화이트박스 기법이다" → X. 기법 이름 6~8개를 화/블로 즉시 분류하는 문제가 제일 흔함. **커버리지 들어가면 무조건 화이트.**

## 5. 통합 테스트 — 하향식/상향식, 스텁/드라이버

**한 칼 구분: 아직 없는 놈을 가짜로 만든다. 하향식은 아래가 없다 → 스텁(하위 가짜). 상향식은 위가 없다 → 드라이버(상위 가짜).**

| | 하향식 (Top-down) | 상향식 (Bottom-up) |
|---|---|---|
| 진행 | 상위 → 하위 (깊이/너비 우선) | 하위 → 상위 (클러스터 묶음) |
| 가짜 모듈 | **스텁 (Stub)** = 미완성 **하위** 대체 | **드라이버 (Driver)** = 테스트 호출용 **상위** 대체 |
| 장점 | 설계 결함 조기 발견 | 하위 모듈 검증 철저, 스텁보다 작성 쉬움 |

암기: **"하-스, 상-드"** (하향식-스텁 / 상향식-드라이버)

> ⚠️ 선지함정: "상향식 통합에는 스텁이 필요하다" → X. "빅뱅 통합은 드라이버·스텁 없이 한 번에" → O. 회귀(Regression) 테스트 = 변경 후 **기존 기능 재확인**도 세트로 자주 나옴.

## 3-4. 암호화 핵심

| | 대칭키 | 공개키(비대칭키) |
|---|---|---|
| 키 | 같은 키로 암·복호화 | 공개키 + 개인키 |
| 장점 | **빠름** | 키 관리·분배 용이, **전자서명 가능** |
| 단점 | **키 배송 문제** | 느림 |
| 대표 | AES, DES, 3DES, SEED, ARIA | RSA, ECC, ElGamal |

**RSA 방향 (최다 함정)**

- **기밀성**: 송신자가 **수신자의 공개키**로 암호화 → 수신자가 **수신자의 개인키**로 복호화
- **전자서명**: 송신자가 **송신자의 개인키**로 서명 → 수신자가 **송신자의 공개키**로 검증

```
 ① 기밀성 — 키 주인 = 수신자
    송신자 ──[수신자 공개키로 암호화]──▶ 암호문 ──[수신자 개인키로 복호화]──▶ 수신자
    → 개인키는 수신자만 가짐 → 수신자만 열 수 있다

 ② 전자서명 — 키 주인 = 송신자
    송신자 ──[송신자 개인키로 서명]──▶ 서명 ──[송신자 공개키로 검증]──▶ 수신자
    → 개인키는 송신자만 가짐 → 송신자만 만들 수 있다 = 부인방지
```

판정 요령: 선지는 **주어(송신자/수신자)만 바꿔치기**한다. 암호화=상대방 공개키, 서명=내 개인키.

## 3-5. 해시 함수

- 입력 길이와 상관없이 **고정 길이** 해시값 생성
- 특징: **일방향성, 역상 저항성, 제2역상 저항성, 충돌 저항성**
- 대표: SHA-2, SHA-3

**해시만 사용했을 때의 한계**: 무결성 확인은 가능하지만, 공격자가 **본문과 해시를 같이 바꿀 수 있음** → 송신자 인증까지 하려면 **MAC** 또는 **전자서명** 필요.

## 3-6. MAC — Message Authentication Code

> [함정] 여기의 MAC은 **Mandatory Access Control이 아님** (3-14와 약어 충돌 주의!)

- MAC = **메시지 + 비밀키**로 인증값 생성
- 보장: **무결성 + 메시지 인증**
- 그러나 송신자·수신자가 **같은 비밀키를 공유**하므로 → **부인방지 불가**
- **HMAC** = 해시 함수 + 비밀키

```
메시지 + 공유 비밀키 → HMAC → MAC 값
```

- 송신자는 [본문 + MAC 값]을 보내고, 수신자는 같은 비밀키로 다시 MAC을 만들어 비교

**핵심: MAC은 본문을 암호화하는 것이 아니다.** (본문은 평문 그대로 갈 수 있음)

### 🔁 기출로 확인

> **📝 기출 | 정보보호론 2016 국가직 #5**
>
> 해시와 MAC의 차이점으로 옳은 것은?

> ② 해시 크기는 일정하지만 MAC는 메시지와 크기가 같아야 한다.

> ④ 공유 비밀키가 있으면 MAC로 무결성 검증이 가능하나 해시로는 불가능하다.

> **→ 정답 ①** — 핵심 차이는 **키 유무**. ③ MAC은 암호화 아님 → 본문과 같이 보냄.

## 3-7. 전자서명

```
메시지 → (해시) → 해시값 → (송신자의 개인키) → 전자서명
```

- 송신: [원문 + 전자서명]
- 수신: ① 원문을 해시 → ② 송신자 **공개키**로 서명 검증 → ③ 두 해시값 비교
- 보장: **무결성 + 송신자 인증 + 부인방지**

**암기: 서명 = 개인키, 검증 = 공개키**

## 3-8. MAC vs 전자서명

| 구분 | MAC | 전자서명 |
|---|---|---|
| 키 | 공유 비밀키 | 개인키/공개키 |
| 무결성 | O | O |
| 송신자 인증 | O | O |
| **부인방지** | **X** | **O** |
| 속도 | 빠름 | 상대적으로 느림 |

```
                                    ┌──────────────────────────┐
                        +부인방지 ▶ │ 전자서명 (개인키/공개키)    │
                ┌───────────────────┤ 무결성 + 인증 + 부인방지   │
     +인증 ▶    │ MAC (공유 비밀키)   │                          │
 ┌──────────────┤ 무결성 + 메시지 인증 │                          │
 │ 해시 (키 X)   │ 부인방지 X          │                          │
 │ 무결성        │ 본문 암호화 아님     │ 단점: 느림                │
 └──────────────┴───────────────────┴──────────────────────────┘
```

> [함정] "MAC은 부인방지를 제공한다" → X (키를 둘이 공유하니, 수신자도 같은 MAC을 만들 수 있음 → 법적으로 "네가 만들었잖아" 반박 가능). 부인방지가 필요하면 무조건 전자서명.

>

> |---|---|---|
> | 송신자 | (가)로 MAC 계산 | (나)로 서명 작성 |
> | 수신자 | (다)로 MAC 계산 | (라)로 서명 검증 |
>
> ① 공유키 / 공개키 / 공유키 / 개인키  
> ② 개인키 / 공유키 / 공개키 / 공유키

>
> **→ 정답 ③** — MAC은 양쪽 다 **같은 공유키**로 재계산 비교. 서명은 개인키 작성 → 공개키 검증.

- **PKI** (Public Key Infrastructure): 공개키를 안전하게 관리하기 위한 전체 체계

## 3-12. Kerberos

- **대칭키 기반** 네트워크 인증 프로토콜
- 핵심: **티켓** 사용, **KDC**(Key Distribution Center), **비밀번호를 네트워크에 직접 전송하지 않음**
- KDC 구성 = **AS**(Authentication Server) + **TGS**(Ticket Granting Server)

```
로그인 → TGT 발급(AS) → 서비스 티켓 발급(TGS) → 서버 접근
```

> [함정] "커버로스는 공개키 기반이다" → X (대칭키). 타임스탬프로 재전송 공격 방지도 세트로 출제.

## 3-14. DAC · MAC · RBAC

> [함정] 여기의 MAC은 **Mandatory Access Control** (3-6의 메시지 인증 코드와 약어만 같음)

**DAC — 임의적 접근통제 (Discretionary)**

- **객체 소유자**가 권한을 결정. 예) Linux 파일 소유자가 `chmod`로 권한 설정
- 특징: 유연, 사용자 중심, 권한 전파 가능, 보안은 MAC보다 약함
- 키워드: **소유자**

**MAC — 강제적 접근통제 (Mandatory)**

- **중앙 정책 / 보안 등급**에 의해 권한 결정. 사용자가 마음대로 권한 변경 불가
- 예: Top Secret > Secret > Confidential
- 키워드: **보안등급 / 중앙통제**
- 대표 모델: **Bell-LaPadula, Biba**

**RBAC — 역할 기반 접근통제 (Role-Based)**

- 사용자에게 직접 권한을 주는 것이 아니라 **역할(Role)에 권한 부여**
- 예: 김철수 → 회계담당자 Role → 결제 조회/승인 권한
- 장점: 조직 권한 관리 편리, **직무 변경 시 Role만 변경**
- 키워드: **역할 / 직무**

**한 줄: DAC = 소유자, MAC = 보안등급, RBAC = 역할**

## 3-15. Bell-LaPadula

- 목적: **기밀성(Confidentiality)**
- **No Read Up**: 자신보다 높은 등급의 정보 읽기 금지 (상위 읽기 금지)
- **No Write Down**: 자신보다 낮은 등급으로 쓰기 금지 (하위 쓰기 금지)
- 이유: 높은 기밀 정보가 낮은 등급으로 **유출**되는 것을 막기 위해

**암기: 벨라 = 기밀성, NRU / NWD**

### 🔁 기출로 확인

> **📝 기출 | 정보보호론 2016 국가직 #10 ⭐**
>
> BLP의 **\*-속성(star property)**이 규정하는 것은?
>
> ① 자신과 같거나 낮은 수준의 객체만 읽을 수 있다.  
> ② 자신과 같거나 낮은 수준의 객체에만 쓸 수 있다.  
> ③ 자신과 같거나 높은 수준의 객체만 읽을 수 있다.  
> ④ 자신과 같거나 높은 수준의 객체에만 쓸 수 있다.  
>
> **→ 정답 ④** — ★-속성 = **No Write Down** → 같거나 위로만 쓰기. ①은 단순 보안 속성(No Read Up).

> **📝 기출 | 정보보호론 2018 국회직 #7**
>
> BLP 특성·규칙으로 옳지 않은 것은?
>
> ① 비밀정보가 허가되지 않은 방식으로 접근되는 것을 방지하는 것이 목표  
> ② 강제적 접근통제의 통제 규칙을 이 모델 기반으로 정의  
> ③ 단순 보안 규칙: 읽으려면 주체 수준 ≥ 객체 수준  
> ④ 스타 보안 규칙: 쓰려면 주체 수준 ≥ 객체 수준  
> ⑤ 강한 스타 규칙: 동일 수준 객체에만 읽기/쓰기 가능  
>
> **→ 정답 ④** — 쓰기는 **주체 ≤ 객체**(위로만). ≥면 아래로 쓰는 거라 유출.

> **📝 기출 | 정보보호론 2017 국회직 #14**
>
> 옳지 않은 것은?
>
> ① DAC는 정보 소유자가 보안 등급을 결정하고 접근제어도 설정하는 모델이다.  
> ② MAC는 사용자 계정에 기반하며, 자원 소유자가 다른 사용자의 보안 레벨을 수정할 수 있다.  
> ③ BLP는 자신보다 높은 레벨 문서에 쓰기는 가능하지만, 낮은 레벨 문서에는 쓰기 권한이 없다.  
> ④ BLP의 목적은 기밀성, Biba는 무결성이다.  
> ⑤ RBAC는 개별 신분이 아니라 조직 내 역할에 따라 허용 여부를 결정한다.  
>
> **→ 정답 ②** — MAC은 **중앙 정책**, 소유자가 레벨 못 바꿈. ③ BLP 위로 쓰기 OK는 맞는 말.

> **📝 기출 | 정보보호론 2016 지방직 #8**
>
> 옳지 않은 것은?
>
> ① 임의적 접근통제는 정보 소유자가 보안 레벨을 결정하고 접근제어를 설정하는 모델이다.  
> ② 강제적 접근통제는 중앙에서 보안 레벨을 붙이고 정책적으로 접근제어를 설정하는 모델이다.  
> ③ 역할 기반 접근통제는 역할에 권한을 부여해 사용자가 자주 변경되는 환경에서 유용하다.  
> ④ Bell-LaPadula는 비밀노출 방지보다 데이터 무결성 유지에 중점을 둔 모델이다.  
>
> **→ 정답 ④** — BLP = **기밀성**. 무결성은 Biba.



## 3-16. Biba

- 목적: **무결성(Integrity)** — Bell-LaPadula와 **반대 방향**
- **No Read Down**: 낮은 무결성의 정보 읽기 금지 (하위 읽기 금지)
- **No Write Up**: 높은 무결성 객체에 쓰기 금지 (상위 쓰기 금지)

**암기: 비바 = 무결성, NRD / NWU**

## 3-17. Bell-LaPadula vs Biba

| 모델 | 목적 | 읽기 | 쓰기 |
|---|---|---|---|
| Bell-LaPadula | **기밀성** | No Read **Up** | No Write **Down** |
| Biba | **무결성** | No Read **Down** | No Write **Up** |

**초압축: 벨라 "위 읽지마, 아래 쓰지마" / 비바 "아래 읽지마, 위 쓰지마"**

```
      Bell-LaPadula (기밀성)              Biba (무결성)
      ┌──────────────┐                   ┌──────────────┐
      │  상위 등급    │                   │ 높은 무결성   │
      └──────────────┘                   └──────────────┘
         ↑ 읽기 ✕ (NRU)                     ↑ 쓰기 ✕ (NWU)
      ┌──────────────┐                   ┌──────────────┐
      │   주체(나)    │                   │   주체(나)    │
      └──────────────┘                   └──────────────┘
         ↓ 쓰기 ✕ (NWD)                     ↓ 읽기 ✕ (NRD)
      ┌──────────────┐                   ┌──────────────┐
      │  하위 등급    │                   │ 낮은 무결성   │
      └──────────────┘                   └──────────────┘
   허용: 아래 읽기 · 위로 쓰기          허용: 위 읽기 · 아래로 쓰기
```

> [함정] 시험장 복원 한 줄: **기밀성은 아래로 새는 게 문제(Down 금지), 무결성은 위가 오염되는 게 문제(Up 금지)**

## 3-18. Clark-Wilson

- 목적: **상업적 시스템의 무결성**
- 핵심: **잘 형성된 트랜잭션(Well-Formed Transaction)** + **직무 분리(Separation of Duties)**

| 구분 | 약어 | 의미 |
|---|---|---|
| 데이터 | **CDI** | 보호해야 하는 핵심 데이터 |
| 데이터 | **UDI** | 검증되지 않은 외부 데이터 |
| 프로그램 | **TP** | 데이터 변환 프로그램 |
| 프로그램 | **IVP** | 무결성 검증 프로그램 |

핵심: 사용자가 중요 데이터를 직접 수정하지 않고 **허가된 프로그램(TP)을 통해서만 변경** (주체 → TP → CDI)

- 예: 은행 직원이 DB에서 잔액을 직접 UPDATE (X) / 승인된 입출금 프로그램을 통해 변경 (O)

**암기: Clark-Wilson = 상업적 무결성 + 직무분리 + 잘 형성된 트랜잭션**

## 4-1. 디스크 스케줄링

**한 칼 구분: "가까운 것부터"면 SSTF, "한 방향으로 쓸고 가면" SCAN 계열. C-가 붙으면 돌아올 때 서비스 없이 점프.**

| 알고리즘 | 개념 | 특징 · 함정 |
|---|---|---|
| **FCFS** | 요청 **도착 순서** 그대로 | 공평, 이동거리 큼 |
| **SSTF** | 현재 헤드에서 **가장 가까운** 요청부터 | 평균 탐색시간 짧음, 먼 요청 **기아** 가능 |
| **SCAN** (엘리베이터) | 한 방향으로 **끝(0 또는 최대 트랙)까지** 가며 처리 → 반대로 돌아오며 처리 | 끝까지 찍고 돈다 |
| **C-SCAN** | 한 방향으로 끝까지 처리 → **반대쪽 끝으로 점프**(서비스 없음) → 같은 방향으로 다시 처리 | 대기시간 균일. 방향이 0쪽이면 **큰 번호부터 내려오며** 이어감 |
| **LOOK** | SCAN인데 끝까지 안 가고 **마지막 요청에서 방향 전환** | |
| **C-LOOK** | C-SCAN인데 **마지막 요청에서 반대편 첫 요청으로 점프** | |

**풀이 시작점**: ① 큐를 오름차순 정렬해서 수직선에 찍고 헤드 위치 표시 → ② 방향 확인 → ③ 구간 거리 더하기.

**대표 예제 (2022 국가직 #20, SSTF)** — 헤드 50, 범위 0~150, 큐: 80, 20, 100, 30, 70, 130, 40 → 총 이동거리?

```
정렬: 20  30  40  [50]  70  80  100  130
50 → 40 (10) → 30 (10) → 20 (10) → 70 (50) → 80 (10) → 100 (20) → 130 (30)
합계 = 10+10+10+50+10+20+30 = 140
```

→ **정답 140**. 20까지 내려간 뒤 가장 가까운 건 70(거리 50). 매 단계 "현재 위치 기준"으로 다시 가장 가까운 것을 고른다.

> ⚠️ 함정: SSTF는 **처음 위치 기준이 아니라 매번 현재 위치 기준**. SCAN은 끝(0/최대)까지 가는 거리 포함, LOOK은 마지막 요청까지만.

## 4-2. 페이지 교체 알고리즘

**한 칼 구분: FIFO = 들어온 순서, LRU = 마지막 사용 시점, LFU = 사용 횟수, OPT = 미래. 셋 다 "가장 ~한 것을 내보낸다".**

| 알고리즘 | 내보내는 페이지 | 특징 · 함정 |
|---|---|---|
| **FIFO** | **가장 먼저 들어온** 페이지 | 구현 쉬움, hit 돼도 순서 안 바뀜. **벨레이디 모순**(프레임 늘려도 부재 증가 가능) |
| **OPT** (최적) | **앞으로 가장 오랫동안 안 쓸** 페이지 | 부재 최소, 미래를 알아야 해서 **구현 불가**(비교 기준용) |
| **LRU** | **가장 오랫동안 사용 안 된** 페이지 | **hit 때도 "최근 사용"으로 갱신**. 과거 기준 OPT 근사 |
| **LFU** | **사용 횟수가 가장 적은** 페이지 | 동률이면 문제 조건(보통 오래된 것) |
| **MFU** | **사용 횟수가 가장 많은** 페이지 | "많이 쓴 건 이제 끝났다" 가정 |
| **NUR / 2차 기회(Clock)** | 참조 비트(·변형 비트) 0인 페이지 | 참조 비트 1이면 0으로 바꾸고 한 번 더 기회 |

관련 개념: 페이지 부재가 너무 잦아 실행보다 교체에 시간을 더 쓰는 현상 = **스래싱(Thrashing)**.

**풀이 시작점**: 참조열을 가로로 쓰고, 아래에 프레임 칸을 그려 매 참조마다 상태를 적은 뒤 부재(F)에 표시. **처음 빈 프레임이 채워지는 것도 부재로 센다.**

**대표 예제 (2022 국회직 #3)** — 프레임 3개, 참조열 3, 1, 2, 4, 1, 4, 3, 2, 1, 2, 3 → LRU / FIFO 부재 횟수?

**LRU** (프레임 안쪽 순서 = 오래 안 쓴 것 → 최근 쓴 것)

| 참조 | 3 | 1 | 2 | 4 | 1 | 4 | 3 | 2 | 1 | 2 | 3 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 프레임 | 3 | 3 1 | 3 1 2 | 1 2 4 | 2 4 1 | 2 1 4 | 1 4 3 | 4 3 2 | 3 2 1 | 3 1 2 | 1 2 3 |
| 부재 | F | F | F | F | | | F | F | F | | |

**FIFO** (프레임 안쪽 순서 = 먼저 들어온 것 → 나중)

| 참조 | 3 | 1 | 2 | 4 | 1 | 4 | 3 | 2 | 1 | 2 | 3 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 프레임 | 3 | 3 1 | 3 1 2 | 1 2 4 | 1 2 4 | 1 2 4 | 2 4 3 | 2 4 3 | 4 3 1 | 3 1 2 | 3 1 2 |
| 부재 | F | F | F | F | | | F | | F | F | |

→ **LRU 7번 / FIFO 7번**. 차이 포인트: 5번째 참조(1) hit 때 **LRU는 1을 맨 뒤(최근)로 옮기고, FIFO는 그대로 둔다** → 7번째 참조(3)에서 내보내는 페이지가 갈림(LRU는 2, FIFO는 1).

> ⚠️ 함정: LRU에서 hit를 그냥 넘기면 FIFO랑 똑같이 풀게 된다. **hit 나면 반드시 순서 갱신.**

## 4-3. 프로세스(CPU) 스케줄링

**한 칼 구분: 실행 중인 걸 뺏을 수 있으면 선점(SRT·RR·MLFQ·선점 우선순위), 못 뺏으면 비선점(FCFS·SJF·HRN·비선점 우선순위).**

| 알고리즘 | 개념 | 선점 | 특징 · 함정 |
|---|---|---|---|
| **FCFS** | **도착 순서**대로 | 비선점 | 짧은 작업이 긴 작업 뒤에서 오래 기다림(호위 효과) |
| **SJF** | **실행시간이 가장 짧은** 것부터 | 비선점 | 평균 대기시간 최소, 긴 작업 **기아** |
| **SRT** | **남은 실행시간이 가장 짧은** 것. 새 프로세스 도착할 때마다 비교 | **선점** | SJF의 선점판. 도착 시점마다 재판정 |
| **RR** | **시간 할당량(quantum)**만큼씩 돌아가며 | **선점** | 시분할용, 기아 없음. quantum이 너무 크면 FCFS화 |
| **우선순위** | 우선순위 높은 것부터 | 둘 다 가능 | 기아 → **에이징(aging)**으로 해결 |
| **HRN** | **(대기시간 + 서비스시간) ÷ 서비스시간**이 큰 것부터 | 비선점 | SJF의 기아 보완 (오래 기다리면 우선순위 상승) |
| **MLQ / MLFQ** | 여러 큐 / 큐 사이 이동 허용 | 선점 | MLFQ는 오래 쓰면 아래 큐로 강등 |

**공식**: 반환시간 = **종료 − 도착**, 대기시간 = **반환 − 실행**

**풀이 시작점**: ① 도착시간 순으로 정렬 → ② 간트차트 그리기(선점형은 **도착 시각마다 멈춰서 재판정**) → ③ 종료 시각 적고 공식 대입.

**대표 예제 (2023 지방직 #19, SRT)** — 대기 시간 총합?

| 프로세스 | 도착 | 실행 |
|---|---|---|
| P1 | 0 | 30 |
| P2 | 5 | 10 |
| P3 | 10 | 15 |
| P4 | 15 | 10 |

```
간트: | P1 | P2 | P4 | P3 | P1 |
      0    5    15   25   40   65

t=5  P2 도착: P1 남은 25 vs P2 10 → P2로 선점
t=10 P3 도착: P2 남은 5  vs P3 15 → P2 계속
t=15 P2 종료, P4 도착: P1 25 / P3 15 / P4 10 → P4
t=25 P4 종료: P1 25 / P3 15 → P3,  t=40 이후 P1
```

| | 종료 | 반환(종료−도착) | 대기(반환−실행) |
|---|---|---|---|
| P1 | 65 | 65 | **35** |
| P2 | 15 | 10 | **0** |
| P3 | 40 | 30 | **15** |
| P4 | 25 | 10 | **0** |

→ **대기 시간 총합 50**.

> ⚠️ 함정: 선점형인데 도착 시각에 재판정을 안 하면 그냥 SJF로 풀게 된다. "평균"인지 "총합"인지 마지막에 꼭 확인.

### 🔁 기출로 확인

> **📝 기출 | 2025 지방직 #16 (RR 큐 순서)**
>
> 타임 슬라이스 4ms 라운드 로빈. 평균 대기 시간은?
> ```
> 프로세스 | 도착 | 실행

> P2       | 1    | 4
> P3       | 2    | 6
> P4       | 3    | 5
> ```
>
> ① 4 ms  
> ② 11 ms  
> ③ 18 ms  
> ④ 44 ms  
>
